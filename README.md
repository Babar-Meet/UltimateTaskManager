# UltimateTaskManager

## Project Name

**UltimateTaskManager** — a native Windows desktop system utility for monitoring and controlling processes, performance, network endpoints, hardware devices, services, startup programs, and user sessions. The application is a single Win32 executable. It does not use any web framework, UI toolkit, or scripting runtime; the entire user interface is built directly on the Win32 common controls and owner-drawn windows.

## Purpose

UltimateTaskManager is a system management utility for Windows. It provides a Task Manager–style experience with additional power-user tooling: real-time process monitoring with per-process CPU and memory statistics, live system performance graphs, network connection inspection and control, hardware device management, Windows service control, startup-application management across user profiles, session/user management, and a "Quick Kill Tools" workspace for bulk port and process termination and forced file deletion.

The application requires administrator rights at runtime (see [Authentication](#authentication)), and it attempts to enable the `SeDebugPrivilege` to widen access to protected processes. When those privileges are unavailable it degrades gracefully rather than failing.

## Highlights

- **Native Win32 application** — C++20, direct Win32 API, common controls, GDI owner-drawn charts. No webview, no scripting runtime, no runtime framework.
- **Dual-strategy process enumeration** — uses the NT API (`NtQuerySystemInformation(SystemProcessInformation)`) as the primary path with a Toolhelp32 fallback.
- **Dynamic ntdll resolution** — system calls such as `NtSuspendProcess` / `NtResumeProcess` are loaded at runtime via `GetProcAddress`, so the binary links only against documented public system libraries.
- **Real-time performance engine** — a dedicated background thread samples the system on an 800 ms cadence and publishes snapshots to the UI via `WM_APP + 42`.
- **Owner-drawn performance charts** — CPU (single or per-core), memory, disk, GPU, and per-adapter network graphs with 90-sample rolling history.
- **Deep OS integration** — PDH disk counters, DXGI GPU enumeration and memory queries, IP Helper network statistics, SetupAPI/CfgMgr device management, WTS session management, SCM service control, and registry-based startup approval handling.
- **Safety-guarded destructive actions** — process termination blocks system-critical PIDs (0, 4, and the app itself), hardware disable is blocked for protected device classes, and forced deletion uses the Restart Manager plus staged-rename retries.
- **Elevated by design** — the application manifest requests `requireAdministrator` and the UI reports elevation and `SeDebugPrivilege` status live in the status bar.

## Features

- **Processes**
  - Full process listing with columns: Name, PID, CPU %, Working Set, Private Bytes, Threads, Handles, Parent PID, Priority, Read bytes, and Write bytes.
  - Live CPU %, memory, and I/O values recomputed on each engine snapshot.
  - Column-header sorting (click to toggle ascending/descending) with a stable secondary sort by PID.
  - Case-insensitive filter on image name or PID.
  - Right-click context menu: End Task, End Process Tree, Suspend, Resume, Set Priority (Idle/Below Normal/Normal/Above Normal/High/Realtime), Set Affinity (All Cores, Core 0, Core 1), Open File Location, Properties.
  - Realtime priority change requires an explicit warning confirmation.

- **Performance**
  - Views: All Stats, CPU, Memory, Disk, Wi-Fi, Ethernet, GPU.
  - CPU: single total graph or per-core graphs (mouse-wheel scrollable); includes sockets/cores/logical processors, base clock (from registry), cache sizes (L1/L2/L3), virtualization flag, and uptime.
  - Memory: used/available, committed vs commit limit, and headroom trend.
  - Disk: read/write MB/s, `% Disk Time`, and average response time via PDH.
  - Network: per-adapter upload/download Mbps (IP Helper byte-delta sampling) with Wi-Fi vs Ethernet breakdown.
  - GPU: per-adapter utilization split into 3D/Copy/Decode/Encode engines, dedicated and shared memory usage via DXGI.
  - Dynamically built navigation buttons for each detected network adapter and GPU.

- **Network**
  - TCP (all states) and UDP endpoint inventory with owning PID and resolved process name.
  - Filters: All, TCP, UDP, Listening, Established.
  - Live text search across protocol, address family, endpoints, state, process name, and PID.
  - Terminate the owner process of a selected endpoint (system PIDs are blocked).
  - Close an active TCP connection via `SetTcpEntry` (DELETE_TCB).

- **Hardware**
  - Enumerate all present devices via SetupAPI (`SetupDiGetClassDevsW` + `DIGCF_ALLCLASSES | DIGCF_PRESENT`).
  - Columns: Name, Class, Status, Location; friendly names with multi-fallback resolution (device property → registry).
  - Enable/disable devices via `CM_Enable_DevNode` / `CM_Disable_DevNode` (with persistent disable fallback).
  - Critical device classes (system, processor, computer, firmware, ACPI, security devices, battery, memory) are protected from disable.

- **Services**
  - Full SCM enumeration of Win32 services (`EnumServicesStatusExW`).
  - Columns: Display Name, Service Name, Status, Startup Type, PID, Account, Description.
  - Start, Stop, and Restart with state-transition waiting and timeout handling.
  - Filters: All, Running, Stopped; text search across service fields.
  - Opens `services.msc` directly.

- **Startup Apps**
  - Enumerates Registry Run, Registry Run (Wow6432Node), and Startup Folder entries.
  - Targets: Current User, System Startup (All Users), All Users + System, or a specific user profile (SID).
  - Reads and writes the Windows `StartupApproved` registry values to enable/disable entries.
  - Resolves executable locations for entries and opens them in Explorer.
  - User-profile discovery via `HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\ProfileList`.

- **Users**
  - Enumerates Terminal Services sessions (WTS API) with account, state, session name, CPU, memory, disk and network rates, and process counts.
  - Per-user process list with CPU, memory, disk, and byte counters, filterable by account.
  - Log off and disconnect sessions (current session is excluded from these actions).

- **Quick Kill Tools**
  - **Port Killer**: given one or more ports, finds owner PIDs from TCP/UDP tables and terminates them (all at once, or one-by-one with confirmation).
  - **Process Killer**: given one or more name patterns, terminates matching processes (all at once, or one-by-one with confirmation).
  - **Force Delete**: browse for a file or folder and force-delete it using the Restart Manager lock detection, process-candidate termination, staged rename, and retries (including an Explorer fallback with shell relaunch).

## Technical Overview

### Application model

The application runs as a single elevated Win32 window (`UTM_MainWindow` class). A background thread owned by `utm::core::engine::MonitorEngine` repeatedly enumerates processes, computes per-process CPU usage from CPU-time deltas, and publishes an immutable snapshot to the UI thread using `PostMessage(WM_APP + 42)`. The UI thread consumes the snapshot and refreshes whichever section is currently visible.

Components forward command/notify handling back into `MainWindow` methods, which keeps all HWND state in one place while distributing per-section logic across files.

## Architecture

### Startup flow

1. `wWinMain` initializes the logger, loads Comctl32, and calls `InitCommonControlsEx`.
2. `PrivilegeManager::InitializePrivileges()` records whether the process is elevated and attempts to enable `SeDebugPrivilege`.
3. A `RuntimeState{isElevated, seDebugEnabled}` is passed into `MainWindow`.
4. `MainWindow::CreateAndShow` registers the `UTM_MainWindow` class and creates the 1460×900 window.
5. On `WM_CREATE`, child controls are created, the engine is configured (`SetRuntimeState`, `SetUiNotification(hwnd, WM_APP+42)`) and started.
6. `RunMessageLoop` pumps messages; engine snapshots arrive as `WM_APP + 42` and drive per-section refresh.

### Window procedure pattern

`WndProcSetup` (registered class proc) intercepts `WM_NCCREATE`, stashes the `MainWindow*` in `GWLP_USERDATA`, swaps in `WndProcThunk`, and delegates. This is the standard "attach the object to a native window" pattern for Win32 C++.

### Snapshot pipeline

```
ProcessEnumerator (NT API / Toolhelp)
   → MonitorEngine::RunLoop  (800 ms cadence)
        → CPU % via (kernel+user) time deltas keyed by (pid, createTime100ns)
        → priority class via OpenProcess + GetPriorityClass
        → PublishSnapshot → mutex-protected copy + PostMessage(WM_APP+42)
   → MainWindow::HandleSnapshotUpdate
        → Refresh process list / performance / visible section + status bar
```

## Core Components

### `utm::core::engine::MonitorEngine` (`src/core/engine/MonitorEngine.cpp`)

- Runs a worker thread that loops until `running_` is cleared; `Stop()` joins the thread.
- Default refresh interval 1000 ms; `MainWindow` constructs it with 800 ms.
- CPU% is computed per process as: `delta100ns / 1e7 / (elapsedSeconds * cpuCount) * 100`, where `delta100ns` is the change in `kernelTime + userTime` between snapshots. The sample key is `(pid << 32) ^ createTime100ns`, which protects against PID reuse.
- Snapshots are published under `snapshotMutex_`; consumers call `GetSnapshot()`.
- Notifications are sent by `PostMessageW(notifyWindow_, notifyMessageId_, 0, 0)` and/or an optional callback.

### `utm::system::ntapi::NtApi` (`src/system/ntapi/NtApi.cpp`)

- Singleton that loads `ntdll.dll` (via `GetModuleHandleW`/`LoadLibraryW`) and resolves `NtQuerySystemInformation`, `NtSuspendProcess`, and `NtResumeProcess`.
- Each wrapper returns `STATUS_NOT_IMPLEMENTED` if the function is unavailable, enabling graceful fallback.
- `HasSuspendResume()` lets callers decide whether to use the NT suspend path or the Toolhelp thread-suspend fallback.

### `utm::system::process::ProcessEnumerator` (`src/system/process/ProcessEnumerator.cpp`)

- `Enumerate()` prefers the NT API path (`SystemProcessInformation`); if it returns nothing, it falls back to Toolhelp32.
- The NT path handles `STATUS_INFO_LENGTH_MISMATCH` by growing the buffer (up to 8 attempts), and parses the packed `SYSTEM_PROCESS_INFORMATION`-equivalent structure directly.
- The Toolhelp path fills memory/IO/times via `GetProcessMemoryInfo`, `GetProcessIoCounters`, and `GetProcessTimes`.

### `utm::tools::process::ProcessActions` (`src/tools/process/ProcessActions.cpp`)

- `SmartTerminate`: posts `WM_CLOSE` to the target's visible windows, waits up to `gracefulTimeoutMs`, then falls back to `TerminateProcess`.
- `TerminateTree`: builds a parent→children map from Toolhelp, terminates children first (bottom-up).
- `Suspend`/`Resume`: prefer `NtSuspendProcess`/`NtResumeProcess`; otherwise suspend/resume every thread individually.
- `SetPriority`/`SetAffinity`: thin wrappers over `SetPriorityClass` / `SetProcessAffinityMask`.
- `OpenFileLocation`/`OpenProperties`: resolve the image path with `QueryFullProcessImageNameW` and invoke Explorer (`explorer.exe /select,"..."`) or the Shell `properties` verb.
- `ForceDeletePath`: multi-stage forced deletion —
  1. Clear read-only attributes (recursively for directories).
  2. Attempt direct delete.
  3. Register files with the Restart Manager (chunked, max 2048 resources) and collect locking PIDs.
  4. Add path-related process candidates and kill lock owners (tree + smart terminate).
  5. Retry deletion (6 attempts, 180 ms apart).
  6. Stage the target by rename (`*.utm_force_delete_*`), then retry.
  7. For directories with no identified lock owners, kill `explorer.exe` candidates, retry, and relaunch Explorer via ShellExecute.

### `utm::system::services::ServiceManager` (`src/system/services/ServiceManager.cpp`)

- Static class over the Service Control Manager.
- `EnumerateServices` uses `EnumServicesStatusExW(SC_ENUM_PROCESS_INFO)`, resolving config details (startup type incl. delayed auto-start, account name, load order group, description) via `QueryServiceConfigW` / `QueryServiceConfig2W`.
- Start/Stop/Restart wait for the target state with a bounded timeout, honoring the service's `dwWaitHint` (clamped 150–1000 ms).

### `utm::system::startup` (three modules)

- `StartupAppsManager` (`src/system/startup/StartupAppsManager.cpp`)
  - Enumerates registry `Run` (HKCU/HKLM) and `Run` under `Wow6432Node`, plus Startup Folders (`FOLDERID_Startup`, `FOLDERID_CommonStartup`, or per-profile paths).
  - Target kinds: current user, system-wide (all users), all users + system, or a specific SID.
  - Expands environment strings in commands and guesses executable paths (`SearchPathW`) for "Open Location".
  - `SetStartupEnabled` refuses entries belonging to other user profiles.
- `StartupApprovalStore` (`src/system/startup/StartupApprovalStore.cpp`)
  - Reads/writes `Explorer\StartupApproved\{Run,Run32,StartupFolder}` REG_BINARY values under HKCU or HKLM.
  - Enabled state: first byte `0x02` (or `0x06`); disabled: `0x03` with a FILETIME-encoded timestamp.
- `StartupProfileDiscovery` (`src/system/startup/StartupProfileDiscovery.cpp`)
  - Reads `HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\ProfileList` to enumerate interactive user profiles (skips SIDs such as S-1-5-18/19/20; includes S-1-5-21-* and S-1-12-1-*).
  - Determines hive-load status and whether each profile is the current user's.

### `utm::system::users::UserSessionManager` (`src/system/users/UserSessionManager.cpp`)

- `EnumerateUserSessions` uses `WTSEnumerateSessionsW`, resolves names via `WTSQuerySessionInformationW`, and aggregates per-session CPU/memory/read/write totals from the shared system snapshot.
- `EnumerateUserProcesses` maps each process to its session account.
- `LogoffSession`/`DisconnectSession` wrap `WTSLogoffSession` / `WTSDisconnectSession`.

### `utm::util::logging::Logger` (`src/util/logging/Logger.cpp`)

- Mutex-guarded `std::wofstream` singleton writing to `%TEMP%\UltimateTaskManager\utm.log` (append mode).
- Levels: Debug, Info, Warning, Error; each line is timestamped (`%Y-%m-%d %H:%M:%S`) and flushed immediately.

### `utm::util::security::PrivilegeManager` (`src/util/security/PrivilegeManager.cpp`)

- `IsProcessElevated` checks `TokenElevation`.
- `EnablePrivilege(SE_DEBUG_NAME)` uses `AdjustTokenPrivileges` and reports `ERROR_NOT_ALL_ASSIGNED` explicitly.

## Authentication

The application does not implement user authentication or identity management. Instead it relies on Windows security:

- **Elevation**: the embedded manifest requests `requireAdministrator` (`resources/app.manifest`), so the process starts elevated (or the OS prompts via UAC).
- **Privilege**: at startup the app enables `SeDebugPrivilege` (when the token allows it) to inspect/control processes that would otherwise be protected.
- **Runtime state**: elevation and `SeDebugPrivilege` status are surfaced in the status bar (`Elevated: Yes/No | SeDebug: Enabled/Unavailable`), and the system managers report access-denied errors gracefully.

## Application Workflow

1. **Startup**: elevate → init logger/common controls → query privileges → create window → start engine.
2. **Continuous monitoring**: engine thread enumerates processes every ~800 ms, computes CPU%, publishes snapshots.
3. **UI refresh**: on each `WM_APP + 42`, the active section refreshes (process list always; network/hardware/services/startup/users per their throttled cadences; performance metrics always recomputed).
4. **User actions**:
   - Processes: sort/filter, context-menu actions (end, tree-end, suspend/resume, priority, affinity, open location, properties).
   - Performance: switch subviews and CPU graph mode; scroll per-core grid.
   - Network: filter/search, terminate owner process, close TCP connection.
   - Hardware: filter/search, enable/disable device (with confirmations and protected-class guards).
   - Services: filter/search, start/stop/restart, open `services.msc`.
   - Startup Apps: choose user target, filter/search, enable/disable, open location.
   - Users: filter/search, log off / disconnect a session.
   - Quick Kill Tools: port killer, process killer, force delete.
5. **Shutdown**: window closed → message loop exits → engine destructor calls `Stop()` (joins worker) → logger flushes/closes.

## Performance

- **Sampling cadence**: engine refresh 800 ms in the app (default 1000 ms in the engine class); per-section throttles as listed in [Configuration](#configuration).
- **CPU accounting**: per-process CPU% is derived from kernel+user time deltas over the refresh window, keyed by `(pid, createTime100ns)` to avoid PID-reuse misattribution; process CPU is clamped to 0–100.
- **Virtual list**: the process list uses `LVS_OWNERDATA`-style virtual rendering via `LVN_GETDISPINFOW` (set-item-count + redraw), so large process sets do not require per-row allocations on each refresh.
- **Rolling history**: all chart series are `std::deque<double>` capped at 90 samples.
- **Throttled scans**: expensive enumerations (network endpoints, hardware devices, services, startup apps, user sessions) are only refreshed when their section is visible and after their throttle interval elapses.
- **Disk counter latency**: PDH disk counters are collected each tick but formatted lazily; GPU engine counters use `PdhGetFormattedCounterArrayW` only when GPUs are present.

## Engineering Decisions

- **Native Win32 over web/embedded frameworks**: the entire UI is hand-built with Win32 controls and GDI owner-draw. This avoids a browser/webview runtime, keeps the binary self-contained, and is consistent with a systems utility that must react at high frequency.
- **NT API with Toolhelp fallback**: `NtQuerySystemInformation(SystemProcessInformation)` gives richer per-process data in one call; Toolhelp32 is the fallback if the NT path is unavailable. ntdll functions are resolved at runtime so the linker never depends on ntdll import tables.
- **Background engine + message-based UI sync**: the 800 ms worker posts `WM_APP + 42` to the window. This keeps all Win32 UI mutations on the UI thread while the engine snapshots under a mutex — a straightforward, race-free design.
- **PID-reuse-safe CPU sampling**: CPU samples are keyed by `(pid, createTime100ns)`, preventing a recycled PID from inheriting stale CPU baselines.
- **Component decomposition with `friend` access**: each UI concern lives in its own translation unit (process list, performance, network, hardware, services, startup, users, quick tools) but all HWND state is centralized on `MainWindow`; `friend` classes forward to `MainWindow` handlers. This keeps the large window class manageable while avoiding a heavyweight MVC layer.
- **Throttled expensive panels**: rather than refreshing all sections every tick, sections refresh on-demand with per-section intervals, keeping the UI responsive.
- **Graceful privilege degradation**: elevation and `SeDebugPrivilege` are detected and surfaced rather than assumed; actions fail with readable error text when privileges are missing.

## Interesting Implementation Details

- **Dynamic ntdll loading**: `NtApi` resolves `NtQuerySystemInformation`, `NtSuspendProcess`, and `NtResumeProcess` via `GetProcAddress` and defines its own `NT_SUCCESS`/NTSTATUS constants in `NtApi.h`, avoiding a hard ntdll dependency.
- **StartupApproved bit semantics**: an entry is "enabled" when the first byte of its `StartupApproved` REG_BINARY value is `0x02` or `0x06`; disabling writes `0x03` plus a `GetSystemTimeAsFileTime` timestamp. This mirrors how Windows itself tracks startup state.
- **Per-user startup scoping**: the app can enumerate startup entries for *other* user profiles by reading `HKEY_USERS\<SID>\...` for loaded hives and reconstructing the per-profile Startup Folder path from `ProfileImagePath`. Toggling is deliberately disabled for foreign profiles.
- **Force-delete staging**: `TryStagePathForDeletion` renames the target to `*.utm_force_delete_<seed>_<n>` (up to 24 rename attempts) so the directory name is freed even if the files inside are still locked, then deletes the staged path.
- **Explorer fallback with relaunch**: when a locked directory has no Restart Manager lock owners, the app kills `explorer.exe` processes (by name match, excluding PID 0/4/self), retries deletion, and relaunches Explorer with `ShellExecuteW` — a well-known Windows admin technique.
- **GPU engine classification**: GPU utilization is broken down by matching PDH instance names for `engtype_3d`, `engtype_copy`, `engtype_videodecode`, and `engtype_videoencode`, mapped back to DXGI adapters via LUID keys.
- **Per-core CPU grid**: per-core utilization comes from `SystemProcessorPerformanceInformation` (idle/total deltas), and the core grid is drawn as an owner-draw control with mouse-wheel scrolling (40 px steps) in both "All Stats" and per-core CPU views.
- **DPI awareness**: the manifest sets both legacy `dpiAware` and `PerMonitorV2`, and window layout recomputes on `WM_SIZE`, so scaling behaves across monitors.
- **Virtual process list**: `ListView_SetItemCountEx` + `LVN_GETDISPINFOW` means the list renders tens of thousands of processes without allocating one item per row per tick.
- **`GetWindowLongPtr`/thunk pattern**: the window class swaps its WndProc on `WM_NCCREATE` to bind a C++ instance to the HWND, a classic pattern used here to keep `MainWindow` state out of globals.
